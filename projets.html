Dossier 01 · Projet de formation

Nettoyage & fiabilisation d'une base clients [secteur]

Code source ↗ Notebook / rapport ↗
Contexte
[Entreprise/mission fictive] disposait d'une base clients de X lignes utilisée pour le reporting mensuel, mais les analyses produisaient des chiffres incohérents d'un mois sur l'autre. Objectif : livrer une base fiabilisée et un protocole de contrôle qualité réutilisable par l'équipe.
Données
  • Source : export CRM au format CSV, ~X lignes, X colonnes
  • Qualité initiale : Y % de doublons, Z % de valeurs manquantes sur les champs clés, formats de dates hétérogènes
  • Limites : aucune donnée de référence externe pour valider certains champs ; historique limité à 18 mois
Démarche
  • Audit qualité initial avec Python (Pandas, ydata-profiling) pour cartographier les anomalies
  • Choix de Pandas plutôt qu'Excel : volumétrie et besoin de reproductibilité (script versionné vs manipulation manuelle)
  • Règles de déduplication et de normalisation documentées et commentées dans le notebook
  • Contrôle qualité automatisé (script réutilisable pour les prochains exports)
Résultats & impact
Base fiabilisée à 99 % sur les champs clés, taux de doublons ramené de Y % à moins de 0,5 %. Le script de contrôle qualité a été conçu pour être relancé à chaque nouvel export, ce qui réduit le temps de fiabilisation mensuel de plusieurs heures à quelques minutes.
Limites & pistes
Certaines anomalies (adresses mal saisies) nécessiteraient un rapprochement avec une API d'adresses pour être corrigées automatiquement. Prochaine étape envisagée : intégrer ce contrôle qualité directement dans le pipeline d'ingestion, en amont du reporting.

Dossier 02 · Projet de formation

Analyse des facteurs d'attrition client

Code source ↗ Rapport ↗
Contexte
La direction commerciale de [entreprise fictive] cherchait à comprendre pourquoi le taux de résiliation avait augmenté de X points en un an, pour prioriser ses actions de rétention sur les segments les plus à risque.
Données
  • Source : base contrats + historique de contacts service client (SQL), ~X clients
  • Qualité : bonne complétude sur les champs contractuels, faible sur les motifs de résiliation (texte libre)
  • Limites : pas de données de satisfaction (NPS) disponibles sur la période étudiée
Démarche
  • Requêtes SQL pour construire une table d'analyse au niveau client (ancienneté, usage, incidents)
  • Analyse statistique (tests du chi², corrélations) pour identifier les variables les plus liées à la résiliation
  • Choix méthodologique : analyse exploratoire d'abord, avant modélisation, pour garder des résultats interprétables et actionnables par des non-techniciens
  • Restitution sous forme de rapport avec visualisations (Matplotlib / Seaborn)
Résultats & impact
Trois facteurs expliquent la majorité des résiliations : plus de 2 incidents non résolus en 6 mois, absence d'usage pendant 3 mois consécutifs, et fin d'engagement contractuel. Recommandation : mettre en place une alerte automatique dès le 2ᵉ incident non résolu.
Limites & pistes
Analyse corrélationnelle, pas causale — impossible d'affirmer que résoudre les incidents plus vite réduirait mécaniquement l'attrition sans test contrôlé. Piste : construire un modèle prédictif (voir Dossier 03) et tester l'impact d'une intervention sur un échantillon pilote.
